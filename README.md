# Journey Support Pass

2026-10-25 DX 통합 요청 1차 구현: 기존 사전등록을 유지하면서, 현장 요청 → 직원 배정 → 도착·지원 → 종료를 별도 흐름으로 추가했다. 미등록 여객도 항공편·서류 없이 `/help`에서 요청하고, 사전등록 여객은 내 등록의 「지금 도움 요청」에서 내용을 불러온다. 직원은 `/staff/requests`에서 처리한다.

구현 범위, 알림 설정, 추가 DB 스키마와 배포 순서는 [docs/dx-integration.md](docs/dx-integration.md)에 있다. 기존 호출·이동지원 흐름은 유지하며 새 통합 요청과 자동 합산하지 않는다. **모든 위치와 서비스 처리는 시연용이며 실제 로봇·차량 출동과 연결되지 않는다.**

다음은 유지 중인 사전등록·탑승권 시연 흐름이다.

여객이 항공권 예매 완료 화면의 링크로 들어와 필요한 도움과 증빙을 한 번 등록하면, 체크인할 때 전자토큰이 탑승권에 저장된다.
출국 당일 교통약자 우대출구에서는 서류 없이 탑승권만으로 확인받고, 공항의 안내 키오스크도 탑승권을 읽어 화면과 길 안내를 그 여객에게 맞춘다.
증빙서류는 공항이 아닌 별도 서버가 보관한다는 구조다. 시제품은 파일을 기기 밖으로 보내지 않고 "냈다"만 받는다. 체크인은 모의 체크인으로 흉내 낸다(2026-10-24, 팀 제안서 「예약 완료 후 연결형 정보입력」).
이름·연락처는 받지 않는다. 받는 것은 항공편과 고른 항목, 증빙 확인 여부뿐이고 출발 후 지운다.
증빙서류(여권 MRZ, 복지카드, 산모수첩, 가족관계증명서)는 휴대전화나 키오스크 안에서 글자 인식(tesseract.js)으로 종류와 나이를 판정하고, 사진과 읽은 글자는 어디에도 보내지 않는다.
공항 입구 안내로봇에서는 등록하지 않은 여객도 탑승권을 찍고 그 자리에서 등록하며, 이동지원(전동차)을 청하고 접수 상태를 본다.

설계는 [docs/spec.md](docs/spec.md) 에 있다. [docs/plans/2026-10-05-webapp-prototype.md](docs/plans/2026-10-05-webapp-prototype.md) 는 예전 구조를 만들 때의 계획이라 지금 구조와 맞지 않는다.

**지금은 모의 데이터 전용이다.** 실제 여객 정보는 기관의 개인정보 검토가 끝난 뒤에만 받는다. 길과 시설 위치도 시연용 모의 자료다.

## 로컬에서 실행

계정이나 외부 서비스 없이 이 컴퓨터 안에서 돈다. DB는 `.data/pglite` 폴더에 저장된다.

```bash
npm install
```

```bash
npm run seed -- --mock-flights
```

```bash
npm run dev
```

`http://localhost:3000` 을 연다.

`seed` 는 개발 서버를 끈 상태에서 실행한다. 직원 구역과 지금 시각 기준의 모의 운항을 넣고, 시범용 접속 코드를 화면에 출력한다. 같은 코드가 [db/seed-zones.json](db/seed-zones.json) 에도 있다. 아래 세 개만 알면 된다.

| 코드 | 어디에 쓰는가 |
|---|---|
| `100100` | 안내데스크 로그인 (`/staff/login`) |
| `200200` | 현장 직원 공통 로그인 (`/staff/login`). 들어가서 근무 구역을 고른다 |
| `300300` | 키오스크 설치 (`/kiosk`) |

이 코드는 모의 데이터 전용이다. 저장소에 공개된 값이라 배포된 곳에는 넣지 않는다. 구역마다 따로 있는 코드도 같은 파일에 있으며, 그 코드로 들어가면 그 구역으로 바로 들어가고 구역을 바꿀 수 없다.

모의 운항 편명은 `MK101`, `MK102`, `MK111`, `MK112`, `MK127`, `MK221`, `MK250`(지연), `MK900`(탑승구 미정), `MK300`, `MC830`(공동운항, 실제 운항 편은 `MK300`), `MK401`(탑승중), `MK402`(탑승마감), `MK403`(결항), `MK501`(제1여객터미널), `MK601`(괌, 한 글자 도시) 이다. 모의 운항은 `seed` 를 실행한 시각 기준으로 몇 분~몇 시간 뒤에 떠나게 들어가므로, 시간이 지나 편이 떠났으면 `seed` 를 다시 실행한다.

같은 곳으로 가는 편이 많은 장면(도착 도시에서 고르기 → 출발 시간대 → 항공사)을 볼 수 있게 오사카로 가는 편 열두 개(`MK7xx`, `MQ7xx`, `MZ7xx`)도 들어간다.

### 한 번 따라 해 보기

직원 로그인과 키오스크 설치는 한 브라우저에서 같은 자리(쿠키)를 쓴다. 그래서 키오스크와 직원 화면은 서로 다른 브라우저나 시크릿 창, 또는 다른 기기에서 연다.

1. **휴대전화로 등록한다.** `/` 에서 「등록 시작하기」를 누른다. 안내받는 방식에서 「큰 글씨로 보여주세요」를 고르면 그 화면부터 글자가 커진다. 동의하고, 이동·찾는 시설·직원 도움을 고른다. 편명에 `MK1` 까지만 넣어도 후보가 뜬다. `MK127` 을 고르고 「등록하기」를 누른다. 패스 화면에 QR과 번호 여섯 자리가 나온다. 번호를 적어 둔다.
2. **안내 키오스크를 설치한다.** `/kiosk` 를 연다. 쓰임새는 「안내 키오스크」, 놓을 자리는 「탑승동 3층 중앙 (116번 탑승구 앞)」, 설치 코드는 `300300` 을 넣는다. 안내 키오스크의 처음 화면이 열린다.
3. **패스를 연다.** 다른 기기에 패스 화면이 떠 있으면 QR을 카메라에 보여 준다. 한 컴퓨터로 해 볼 때는 「고유 일련 번호 누르기」를 눌러 적어 둔 번호를 누른다. 화면이 고른 방식(큰 글씨 등)으로 바뀌고 항공편, 탑승구 가는 길, 가까운 시설이 나온다.
4. **직원을 부른다.** 오른쪽 위의 「직원 부르기」를 누른다. "직원을 부르고 있습니다"가 뜬다.
5. **직원 화면에서 받는다.** 다른 브라우저(또는 시크릿 창)에서 `/staff/login` 에 `200200` 을 넣고 근무 구역으로 탑승동의 「중앙부」를 고른다(다른 구역을 골랐으면 「전체」를 눌러 본다). 방금 호출이 고른 항목, 항공편과 함께 보인다. 「가겠습니다」를 누르면 키오스크가 "직원이 오고 있습니다"로 바뀐다. 「도움 마침」을 누르면 끝난다.
6. **끝낸다.** 키오스크에서 「안내 끝내기」를 누르면 만족도 한 문항이 나오고 처음 화면으로 돌아간다. `100100` 으로 로그인해 「오늘 현황」을 열면 방금 한 일이 숫자로 보인다.

등록 키오스크를 보려면 `/kiosk` 에서 쓰임새를 「등록 키오스크」로 골라 다시 설치한다.

### 시연용 패스

장면마다 다른 안내가 나오도록 미리 골라 둔 패스 열 장을 만들고, QR을 한 장짜리 그림과 A4 PDF 로 뽑는다. 개발 서버를 켠 채로 실행한다.

```bash
npx tsx scripts/remote-demo.ts "저장할 폴더" --local
```

배포된 곳에 만들려면 `--local` 을 뺀다. 이때는 저장소에 올리지 않는 `.env.deploy.local` 의 값을 쓴다.

```bash
npx tsx scripts/remote-demo.ts "저장할 폴더"
```

- 폴더에 `시연용_패스QR.png` 와 `시연용_패스QR.pdf` 가 생긴다. 화면에는 번호와 장면 이름만 출력한다.
- 모의 데이터 모드에서만 동작한다. 설치된 Chrome(없으면 Edge)으로 그림을 뜬다.
- 다시 실행하면 모의 항공편에 걸린 등록은 모두 지워지고(그 패스는 못 쓰게 된다) 새로 만들어진다.
- 모의 운항을 지금 시각 기준으로 1~16시간 뒤에 떠나도록 다시 넣는다. 떠난 뒤에는 등록이 지워지므로 그때 다시 실행한다.
- 장면 목록은 [src/lib/demo.ts](src/lib/demo.ts) 에 있다. 장면 이름은 QR을 고르기 쉽게 붙인 것이고 서버에 저장하지 않는다.

## 검사

```bash
npm test
```

업무 규칙(등록, 패스, 직원 호출, 삭제, 측정값, 접속 코드와 잠금, 길 계산, 운항 수집, QR 인식)을 메모리 DB 로 검사한다.

화면은 실제 브라우저로 처음부터 끝까지 눌러 본다. 이 컴퓨터의 개발 서버에만 쓴다. 설치된 Chrome(없으면 Edge)을 새 프로필로 띄우므로 평소 쓰는 브라우저에는 영향이 없다.

```bash
# 1) 개발 서버를 끄고 (처음 한 번. 구역과 접속 코드를 넣는다)
npm run seed
# 2) 개발 서버를 켜고
npx tsx scripts/e2e.ts
```

- 모의 운항은 점검이 시작할 때 지금 시각 기준으로 스스로 다시 넣는다. 여객도 점검이 스스로 등록한다.
- 결과는 [docs/scenario-checklist.md](docs/scenario-checklist.md) 에 항목별로 적힌다. 통과와 실패는 그 파일에서 본다. 화면 그림은 `.e2e-shots/` 에 번호 순으로 저장된다(`SHOTS_DIR` 로 바꿀 수 있다).
- 여러 번 돌리면 오늘 현황의 숫자가 쌓인다. 숫자까지 깨끗하게 보려면 1)에서 `.data/pglite` 폴더를 지우고 시작한다.
- 카메라 QR 읽기는 패스 QR 그림을 가짜 카메라 영상으로 넣어 확인한다. 진짜 카메라와 조명, 스티커 프린터는 사람이 따로 확인한다(명세 11장).
- 그림을 뜨는 화면마다 접근성 자동 점검(axe-core, WCAG 2.2 AA 까지)을 함께 돌린다. 화면 읽기 프로그램으로 실제로 써 보는 것을 대신하지 않는다.

## 배포

**주소: https://journey-support-pass.vercel.app** (모의 데이터 전용)

| 무엇 | 어디 |
|---|---|
| 화면과 서버 | Vercel 프로젝트 `journey-support-pass`, 서울 리전(icn1) |
| DB | Vercel Storage 로 만든 Supabase, 서울 리전. 연결 주소는 Vercel 이 `POSTGRES_URL` 로 넣어 준다 |
| 코드와 배포 | GitHub 비공개 저장소 `rkdals0121/journey-support-pass`. `main` 에 push 하면 자동으로 배포된다 |

DB 연결 값은 Vercel 에서 잠겨 있어 꺼내 볼 수 없다. 그래서 이 컴퓨터에서 DB 에 직접 접속하지 않고, 배포된 서버의 초기 설정 통로(`/api/admin/setup`)를 불러 서버가 직접 넣게 한다.

```bash
npx tsx scripts/remote-setup.ts
```

- 테이블과 직원 구역(접속 코드 포함)을 넣는다. 여러 번 실행해도 안전하다. 패스는 등록할 때 만들어지므로 미리 만들지 않는다.
- **배포한 뒤에 꼭 한 번 실행한다.** 구조를 바꾸면서 테이블이 바뀌었다. 배포된 서버는 테이블을 스스로 고치지 않으므로, 이 명령을 실행하기 전에는 새 화면이 제대로 돌지 않는다.
- **키오스크 설치 코드가 있어야 한다.** 이 명령은 `db/zone-codes.local.json` 에서 배포용 코드를 읽는다. 켜져 있는 모든 자리의 코드가 있어야 하고, 이번에 `kiosk` 자리가 새로 생겼다. `kiosk` 의 코드가 없으면 "접속 코드가 없는 구역: kiosk" 로 끝나고 아무것도 넣지 않는다.

이 명령은 저장소에 올리지 않는 파일 두 개를 읽는다. 다른 컴퓨터에서 실행하려면 이 파일을 옮겨야 한다.

| 파일 | 내용 |
|---|---|
| `.env.deploy.local` | `BASE_URL`(배포 주소), `CRON_SECRET`(Vercel 에 넣은 것과 같은 값) |
| `db/zone-codes.local.json` | 배포용 접속 코드. `{ "자리 id": "코드" }` 모양이다. 자리 id 는 `db/seed-zones.json` 의 `id` 와 같다. **배포된 곳의 직원 로그인과 키오스크 설치에 쓰는 코드는 여기서 확인한다** |

`db/seed-zones.json` 에 적힌 코드(`100100` 등)는 저장소에 공개된 값이라 배포 DB 에는 넣지 않는다. 이 컴퓨터의 `localhost:3000` 에서만 쓴다.

배포된 곳은 실제 운항 정보를 받는다. 정해진 장면을 보여줘야 하는 시연 때는 위의 시연용 패스 명령을 쓴다(모의 운항도 함께 넣는다). 모의 운항만 넣거나 지우려면 아래를 쓴다.

```bash
npx tsx scripts/remote-setup.ts --mock-flights
```

```bash
npx tsx scripts/remote-setup.ts --clear-mock
```

### 측정값 내려받기

```bash
npx tsx scripts/remote-metrics.ts
```

배포된 곳의 최근 14일 측정값을 화면에 요약해 보여주고 `out/summary.json` 에 저장한다. 끝에 숫자를 붙이면 그 일수만큼 받는다. 제안서의 기대 효과 세 가지에 해당하는 건수와 가운데값뿐이며, 항공편이나 여객이 고른 항목은 들어 있지 않다(명세 5.3).

### 예약 실행

| 작업 | 지금 | 정식 운영 전에 |
|---|---|---|
| 운항 수집 (`/api/cron/poll-flights`) | 한 시간에 한 번 (Vercel Cron) | 5분 간격으로 (인증키의 일일 호출 한도 확인 후) |
| 삭제 (`/api/cron/purge`) | 한 시간에 한 번 (Vercel Cron) | 10분 간격으로 |

Vercel 무료 요금제는 예약 하나가 하루 한 번까지만 돈다. 그래서 [vercel.json](vercel.json) 에 시각이 다른 예약을 24개씩 넣어 한 시간 간격을 만들었다. 무료 요금제의 예약은 정해진 분에 정확히 돌지 않고 그 시간대 안의 아무 때나 돈다. 한 시간 간격이면 공공데이터 호출은 하루 약 310회다.

한 시간 간격인 동안에는 탑승구 변경이 최대 한 시간 늦게 반영된다. 무료 요금제의 예약은 그 시간대 안의 아무 때나 돌아 정상일 때도 두 수집 사이가 두 시간 가까이 벌어질 수 있다. 그래서 마지막 수집 성공이 135분(수집 간격의 두 배 + 15분)보다 오래되면 안내 화면과 패스 화면에 "운항 정보가 늦어지고 있습니다. 탑승구는 전광판에서 한 번 더 확인해 주세요"가 뜬다. 시범에 쓰려면 아래 방법으로 간격을 줄이고 [src/lib/config.ts](src/lib/config.ts) 의 `pollMin` 도 함께 바꾼다.

간격을 줄이려면 Supabase SQL 편집기에서 `pg_cron` 과 `pg_net` 확장을 켜고 아래를 실행한다. `CRON_SECRET값` 자리에는 Vercel 에 넣은 값을 넣는다.

```sql
select cron.schedule('poll-flights', '*/5 * * * *', $$
  select net.http_get(
    url := 'https://journey-support-pass.vercel.app/api/cron/poll-flights',
    headers := '{"Authorization": "Bearer CRON_SECRET값"}'::jsonb,
    timeout_milliseconds := 280000
  );
$$);

select cron.schedule('purge', '*/10 * * * *', $$
  select net.http_get(
    url := 'https://journey-support-pass.vercel.app/api/cron/purge',
    headers := '{"Authorization": "Bearer CRON_SECRET값"}'::jsonb
  );
$$);
```

### 운항 API 실측

운항 정보를 하루 동안 따로 받아 기록해 본다.

```bash
ICN_API_KEY="디코딩 키" npx tsx scripts/probe-poll.ts
```

5분마다 받아 `out/probe-YYYYMMDD.jsonl` 에 한 줄씩 남긴다. 한 번만 받아 보려면 끝에 `--once` 를 붙인다. 이 기록으로 하루 호출 횟수가 인증키 한도 안에 드는지, 탑승구 변경이 하루 몇 건 잡히는지, 실패하거나 늦는 회차의 비율을 본다. 2026-10-05 에 한 회 받아 본 결과는 명세 7.5 에 있다.

### 배포 환경에서 아직 약한 곳

- **DB 연결이 서버 인증서를 검증하지 않는다.** 통신은 암호화되지만 상대가 진짜 Supabase 인지 확인하지 않는다([src/lib/db.ts](src/lib/db.ts) 의 `pgOptions`). 실제 여객 정보를 받기 전에 Supabase 인증 기관 인증서를 넣어 검증을 켜야 한다.
- **삭제가 한 시간에 한 번 돈다.** 패스는 출발 30분 뒤부터 열리지 않지만, 자료가 실제로 지워지는 것은 그보다 최대 한 시간 늦다. 실제 정보 전에 10분 간격으로 바꿔야 한다.
- **실제 운항 정보는 한 시간에 한 번만 갱신된다.**
- **직원 화면은 켜 두어야 호출이 보인다.** 화면을 꺼도 오는 알림은 없다.

## 아직 임시이거나 모의인 것

- **길과 시설 위치는 모의 자료다.** 터미널을 한 줄로 늘어선 탑승구로 단순하게 보고 탑승구 번호로 위치를 정했다. 거리, 시설 위치, 엘리베이터 위치, 키오스크 자리가 모두 지어낸 값이다. 실제 운영에는 기관의 실내 지도와 시설 목록이 있어야 한다(명세 8장).
- **여객 정보는 모의 데이터다.** `DATA_MODE=mock` 이며 모든 화면 위에 "시범 운영 · TRIAL" 띠가 뜬다.
- **탑승동 세 구역(중앙부·중간·끝단)은 임시값이다.** 탑승구 번호가 중앙에서 먼 순서로 나눴다.
- **제1여객터미널 구역 경계는 추정치다.** 구역 이름에 "경계 추정"을 붙였다.
- **키오스크 자리마다 호출을 받는 구역도 임시로 정했다.** 보안검색 전 자리 세 곳의 호출은 모두 안내데스크로 간다.
- **탑승 마감은 추정값이다.** 공공데이터가 "탑승마감"을 알려 주기 전까지는 출발 10분 전으로 계산하고 화면에 "추정"이라고 적는다.
- **직원 로그인과 키오스크 설치는 접속 코드다.** 정식 운영 시 직원 계정 인증으로 바꾼다.
- **스티커 인쇄는 브라우저의 인쇄 기능을 쓴다.** 실물 프린터로는 아직 찍어 보지 않았다.
- **소리 안내는 기기에 들어 있는 목소리를 쓴다.** 기기에 그 언어의 목소리가 없으면 제대로 읽지 못한다.

사람이 직접 확인해야 하는 것은 명세 11장에 모았다.
