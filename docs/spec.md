# Journey Support Pass 웹앱 개발 명세

- 기준 문서: 28차 프로포절 (부록 A를 구체화한 문서)
- 작성일: 2026-10-05
- 상태: 시제품을 배포함 (https://journey-support-pass.vercel.app, 여객 정보는 모의 데이터, 운항 정보는 실제). 구현·배포 현황과 남은 일은 14장

## 1. 목적과 범위

여객이 필요한 도움을 한 번 등록하고, 인천공항운영서비스 직원이 패스의 QR을 스캔해 그 내용과 항공편·탑승구를 한 화면에서 확인하게 한다.

### 이번에 만드는 것

| 화면 | 사용자 | 프로포절 단계 |
|---|---|---|
| 등록 화면 | 여객 | 1단계 |
| 안내데스크 화면 (패스 연결, 대신 입력, 재발급) | 안내데스크 직원 | 1단계 |
| 직원 화면 (구역 목록, 스캔, 여객 카드, 응대 기록) | 현장 직원 | 2단계 |
| 운항 정보 수집 | 서버 자동 실행 | 3단계 |

### 이번에 만들지 않는 것

- 여객 화면 (내 항공편, 헬프콜, 등록 수정)
- 관리 화면 (집계 조회). 시범 기간 집계는 DB에서 직접 내려받아 계산한다.
- 혼잡도·예상 이동시간 (부록 B)
- 외국어 화면. 한국어만 제공한다.
- 직원 개인 계정. 시범 기간은 구역별 접속 코드를 쓴다.

### 데이터 수준

시범은 모의 데이터로 한다. 다만 기관의 개인정보 검토가 끝나면 코드 수정 없이 실제 정보를 받을 수 있도록, 접근 통제·자동 삭제·조회 기록을 처음부터 구현한다.

## 2. 설계에서 확정한 사항

프로포절 문장만으로는 구현할 수 없어 정한 것들이다. 11장에 프로포절 쪽 수정 사항을 따로 모았다.

| 번호 | 결정 | 이유 |
|---|---|---|
| D1 | 운항 조회 웹과 분리된 새 프로젝트로 만든다 | 공개 사이트와 민감정보 화면을 한 배포에 두지 않는다 |
| D2 | 번호를 둘로 나눈다. 접수 번호(등록 완료 화면)와 패스 번호(패스에 사전 인쇄) | 사전 인쇄한 패스에는 나중에 발급되는 번호를 담을 수 없다 |
| D3 | 패스에 날짜를 인쇄하지 않는다. 만료는 서버가 처리한다 | 날짜를 인쇄하면 매일 새로 찍어야 한다 |
| D4 | "내 구역 여객"은 여객 항공편의 탑승구가 속한 구역으로 정한다 | 시스템은 여객의 현재 위치를 알 수 없다 |
| D5 | 탑승 마감은 공공데이터의 상태(탑승마감)를 우선 쓰고, 그 전에는 "출발 시각 − 10분"으로 계산해 "추정"으로 표시한다 | 공공데이터에 탑승 마감 시각은 없지만 탑승중·마감예정·탑승마감 상태는 실시간으로 온다 (2026-10-05 실측) |
| D6 | 운항 정보는 5분 간격으로 받아 DB에 저장하고, 화면은 그 사본을 읽는다 | 스캔마다 호출하면 호출 한도와 응답 지연에 걸린다 |
| D7 | 탑승동 구역은 프로포절 기준(중앙부·중간·끝단)을 쓴다 | 운항 조회 웹의 남측·중앙·북측 구분은 추정치이고 프로포절 집계와 다르다 |
| D8 | 직원은 개인이 아니라 구역으로만 기록한다. 현장 직원은 공통 코드 하나로 들어와 근무 구역을 스스로 고른다 | 프로포절의 "개인별 평가에 쓰지 않는다"를 구조로 보장한다. 구역마다 코드를 따로 두면 12개를 외워야 해서 현장에서 쓰기 어렵다 (2026-10-07 변경) |
| D9 | 패스는 일회용이다. 출발 후 영구 만료하고 다시 연결하지 않는다 | 프로포절이 출국 후 회수·폐기로 정했다. 여객이 들고 나간 패스가 시스템에 "쓸 수 있는 패스"로 남으면 장부와 실물이 어긋난다 |

## 3. 구성

| 역할 | 선택 | 비고 |
|---|---|---|
| 화면과 서버 | Next.js (App Router, TypeScript), Vercel 배포 | 새 저장소, 새 Vercel 프로젝트 |
| DB | Supabase Postgres, 서울 리전 | 국내 리전에 저장 |
| 예약 실행 | Supabase pg_cron 이 앱의 `/api/cron/*` 경로를 호출 | 운항 수집(5분), 삭제(10분). 호출에는 비밀 값이 필요하다 |
| QR 스캔 | 브라우저 카메라 (BarcodeDetector, 미지원 기기는 jsQR) | 앱 설치 없음 |

브라우저는 DB에 직접 접속하지 않는다. 모든 읽기·쓰기는 서버 경로를 거치고, DB는 서버 전용 키로만 열린다. 테이블에는 행 수준 보안을 켜고 공개 정책을 두지 않는다.

기존 운항 조회 웹에서 가져오는 것은 세 가지다.

- `scripts/collect.py`의 응답 항목 해석 규칙 (`FIELD_MAP`, `TERMINAL_CODE`)
- `data/airports.json`, `data/airlines.json` (한글 이름)
- `data/zones.json`의 제2여객터미널 구역 (검증된 값)

### 4.2 여객 등록

한 화면에 질문 하나만 둔다. 글자는 크게, 선택지는 눌러서 고르는 버튼으로 만든다.

1. **동의**: 수집 항목, 보는 사람(인천공항운영서비스 직원), 지우는 것(이름·항공편·필요한 도움은 출발 후 삭제), 남는 것(교통약자 구분과 응대한 구역·시각은 누구의 것인지 알 수 없는 통계로 남음)을 적는다. 문구는 5.2의 삭제 범위와 같아야 한다. 동의하지 않으면 "기존 안내와 지원을 그대로 받으실 수 있습니다"를 보여주고 끝낸다.
2. **교통약자 구분** (복수 선택)
3. **필요한 도움** (복수 선택, 묶음별로 표시)
4. **이름과 편명**: 편명을 두 글자 이상 치면 오늘과 내일 출발하는 편 가운데 그 글자로 시작하는 편을 자동으로 보여준다(여덟 편까지, 정확히 같은 편명이 맨 위). 편명·도착지·출발 시각이 한 줄씩 나오고 여객이 맞는 편을 누른다. 찾지 못하면 "편명을 다시 확인해 주세요"와 함께 안내데스크 안내를 보여준다.
5. **확인**: 이름·항공편·구분·도움을 한 화면에 보여주고, 항목마다 "고치기"로 그 단계에 돌아갈 수 있다.
6. **완료**: 접수 번호 네 자리를 크게 표시하고 "안내데스크에서 이 화면을 보여 주세요"라고 적는다. 이름·편명·도착지·출발 시각을 함께 보여주어 직원이 대조한다.

선택 항목은 프로포절 1단계 2)와 같은 문구와 순서를 쓴다.

### 4.3 안내데스크

**등록 목록**

패스 연결 탭에는 패스를 기다리는 등록이, 재발급 탭에는 패스가 연결된 등록이 목록으로 나온다. 이름, 편명, 접수 번호(또는 지금 패스 번호), 고른 항목이 보이고 누르면 바로 다음 단계로 넘어간다. 여객이 접수 번호를 잊었을 때 이 목록에서 찾는다. 여러 여객의 이름이 한꺼번에 보이는 화면이므로 열어 본 기록을 남긴다.

**등록 취소**

잘못 들어온 등록이나 여객이 원하지 않는 등록은 안내데스크에서 취소한다. 확인 창을 한 번 거치며, 출발 후 삭제와 같은 방식으로 사람을 알 수 있는 값을 지우고 연결된 패스는 끝낸다. 

**등록 내용 고치기**

이름을 잘못 적었거나 편이 바뀌었을 때 안내데스크에서 고친다. 동의는 다시 받지 않고, 고른 값이 채워진 채로 구분 → 도움 → 이름·항공편 → 확인 순서로 지나간다. 패스가 이미 연결되어 있으면 패스는 그대로 두고 내용만 바뀐다. 편이 바뀌면 그 편의 탑승구가 속한 구역 목록으로 옮겨 간다. 고친 사실은 조회 기록에 남는다. 여객 본인은 고치거나 취소할 수 없고 안내데스크에 요청한다.

**패스 연결**

1. 여객이 보여준 접수 번호를 입력한다. 또는 등록 목록에서 고른다.
2. 이름, 편명, 선택 항목이 뜬다. 직원이 여객 화면과 대조한다.
3. 사전 인쇄한 패스의 QR을 스캔한다. 패스가 이 등록 건에 연결되고 사용 중 상태가 된다. 단말의 카메라를 쓸 수 없으면 패스에 인쇄된 번호 네 자리를 입력한다. 미사용 패스의 번호만 받는다.
4. 실물 패스를 번호 순으로 쌓아 두었다면 "자동 배정"을 누른다. 번호가 가장 작은 미사용 패스가 연결되고, 그 번호가 화면에 크게 뜬다. 직원은 그 번호의 패스를 건넨다.

연결을 마치면 패스 번호를 크게 보여주어 건넬 패스와 대조하게 한다. 화면 위쪽에는 남은 미사용 패스 장수가 항상 보이고, 5장 이하가 되면 붉게 표시한다.

**새로 등록 (종이 체크리스트, 대신 입력)**

여객 등록과 같은 질문을 같은 순서로 보여준다. 시작할 때 경로를 고른다(종이 체크리스트 / 직원이 대신 입력). 입력을 마치면 접수 번호 없이 바로 패스 스캔으로 넘어간다.

**재발급**

패스가 연결된 등록 목록에서 이름이나 편명으로 걸러 찾는다. 접수 번호 조회는 패스 연결 전의 등록만 찾으므로 재발급에는 쓰지 않는다. 두 조회는 서로 다른 경로다.

- 찾는 대상은 패스가 연결된 등록뿐이다.
- 같은 편에 이름이 같은 여객이 여럿이면 후보마다 교통약자 구분과 필요한 도움을 함께 보여주고, 직원이 여객에게 확인해 고른다.
- 본인 확인(탑승권의 이름·편명 대조)은 화면이 아니라 응대 절차서에서 정한다.
- 새 패스를 먼저 연결한 뒤 기존 패스를 폐기한다. 폐기한 패스는 다시 쓰지 않는다.

### 4.4 현장 직원

**목록 (`/staff`)**

- 로그인한 구역의 탑승구로 가는 등록 여객을 보여준다.
- 탑승 마감 추정 시각이 가까운 순서로 정렬한다.
- 마감 30분 이내는 붉게 표시한다.
- 같은 터미널의 탑승구 미정 편은 목록 아래 "탑승구 미정" 묶음에 둔다.
- 30초마다 다시 읽는다.
- 화면 위쪽에 "운항 정보 14:35 기준"을 항상 표시한다.
- 화면 아래쪽에 고정 메뉴(여객 목록 / 패스 스캔 / 안내데스크)를 둔다.
- "내 구역 / 전체"를 바꿔 볼 수 있다. 전체에서는 다른 구역 여객이 구역 이름과 함께 나온다. 여객이 탑승구와 다른 곳에서 도움을 청할 때 쓴다.
- 이름이나 편명으로 찾을 수 있다. 찾을 때는 전체 구역에서 찾는다. 소문자나 일부만 입력해도 된다.
- 내 구역만 볼 때는 다른 구역 여객의 이름을 서버가 보내지 않고 건수만 보낸다. 전체를 볼 때는 조회 기록을 남긴다(같은 기기는 10분에 한 번).
- 여객마다 소통 방식과 필요한 도움을 줄인 말과 그림으로 보여준다. 소통 방식은 어두운 색으로 맨 앞에 둔다.
- 다른 직원이 응대 중이거나 응대를 마친 여객은 "탑승동 끝단 응대 중", "탑승동 끝단 응대 완료 13:05"처럼 구역과 시각으로 표시한다.
- 탑승구가 바뀐 여객은 "탑승구 변경 · 이전 112"를 붉게 표시한다.

**스캔 (`/staff/scan`)**

웹앱 안에서 스캔하면 여객 카드로 넘어간다. 휴대전화 기본 카메라로 찍어도 `/p/{token}`을 거쳐 같은 카드로 넘어간다. 카메라를 쓸 수 없으면 패스 번호 네 자리를 입력한다.

**여객 카드 (`/staff/case/{id}`)**

프로포절 2단계 3)의 순서대로 위에서부터 배치한다.

1. 소통 방식 (감각·소통 묶음 선택 항목)
2. 교통약자 구분
3. 이름
4. 필요한 도움 (이동, 환경 묶음)
5. 동반자 유무, 유모차
6. 항공편, 출발 시각 (지연이면 변경 시각과 함께)
7. 탑승구. 직전 수집에서 바뀌었으면 "변경됨 · 이전 112"를 함께 표시한다.
8. 탑승 마감까지 남은 시간 (추정)
9. 앞선 응대. 이 여객을 앞서 응대한 구역과 시각을 보여준다. 다음 구역 직원이 같은 것을 다시 묻지 않게 하려는 것이다. 카드를 열어 보기만 한 것은 넣지 않고, 응대 시작을 누른 것만 넣는다. 직원 개인은 남지 않는다.
9-1. 가까운 교통약자 시설 (해당 구역의 엘리베이터, 장애인 화장실, 대기 지점)
10. 응대 시작 / 응대 완료 버튼

응대 기록은 다음 규칙으로 만든다.

- 기록은 카드를 여는 순간(스캔 또는 번호 조회) 만들고 스캔 시각을 적는다. 응대 시작을 누르면 같은 기록에 시작 시각을, 응대 완료를 누르면 완료 시각을 채운다.
- 같은 구역이 끝내지 않은 기록이 있으면 새로 만들지 않고 그 기록을 다시 연다. 카드를 여러 번 열어도 기록은 하나다.
- 다른 구역의 직원이 같은 패스를 스캔하면 그 구역의 새 기록이 생긴다. 인계는 이 방식으로 처리한다.
- 직원을 구역으로만 구분하므로, 같은 구역의 두 직원이 같은 여객을 동시에 열면 한 기록을 함께 쓴다. 먼저 누른 응대 시작만 기록되고, 나중에 연 직원의 화면에는 응대 완료 버튼이 보인다.
- 응대 완료 뒤 다시 스캔하면 새 기록이 생긴다.

### 4.5 QR 분기 (`/p/{token}`)

| 조건 | 결과 |
|---|---|
| 직원 로그인 없음 | "직원 전용 화면입니다" |
| 직원 로그인, 연결되지 않은 패스 | "연결되지 않은 패스입니다" (안내데스크 구역이면 패스 연결로 이동) |

| 직원 로그인, 사용 중인 패스 | 여객 카드로 이동, 조회 기록 남김 |

토큰이 존재하지 않는 경우에도 로그인 없는 사람에게는 같은 "직원 전용 화면입니다"를 보여준다. 토큰의 존재 여부가 바깥에 드러나지 않게 한다.

### 5.2 보관과 삭제

| 시점 | 처리 |
|---|---|
| 변경 출발 시각 + 30분 경과, 또는 상태가 출발로 바뀜 | 아래 삭제 범위대로 처리. 패스는 `expired`로 끝냄 |
| 결항 | 화면에 결항으로 표시하고 유지. 다음 날 04:00에 삭제 |
| 예정 출발 시각 + 24시간 | 위 조건과 무관하게 삭제 (안전장치). 운항 정보가 사라진 등록은 등록 후 48시간 |
| 패스 연결 없이 등록 후 24시간 | 삭제 |
| 조회 기록, 수집 기록 | 90일 후 삭제 |

**삭제 범위**

"삭제"는 등록 행 자체를 없애는 것이 아니라, 사람을 알 수 있는 값을 비우고 다른 기록과의 연결을 끊는 것이다. 동의 화면의 문구는 이 표와 같아야 한다.

| 대상 | 지우는 것 | 남는 것 |
|---|---|---|
| 등록 건 | 이름, 편명과 날짜, 필요한 도움, 접수 번호 | 교통약자 구분, 등록 경로, 동의·작성·제출·연결 시각, 수정 횟수. 상태는 `expired` |
| 패스 | 등록 건과의 연결, 연결 시각 | 토큰, 패스 번호, 끝난 상태(`expired` 또는 `revoked`) |
| 응대 기록 | 등록 건과의 연결 | 구역, 스캔·시작·완료 시각, 교통약자 구분, 지원 종류(묶음 단위), 탑승구 위치 구분 |
| 조회 기록 | 등록 건과의 연결 | 시각, 구역, 행위 |

남는 값만으로는 누구의 것인지 알 수 없다. 다만 응대 시각과 구역, 교통약자 구분이 함께 남으므로, 여객 수가 아주 적은 시간대에는 추정 가능성이 있다. 이 점은 기관 개인정보 검토에서 확인받는다.

삭제할 때 응대 기록에 지원 종류와 탑승구 위치 구분을 채운다. 지원 종류는 묶음 단위로만 남긴다.

| 필요한 도움 코드 | 남는 지원 종류 |
|---|---|
| `mov_*` | 이동 |
| `com_*` | 감각·소통 |
| `env_*` | 환경 |
| `acc_*` | 동반 |

삭제 작업은 10분마다 돈다.

### 5.3 자동으로 남는 측정값

| 프로포절 지표 | 계산 |
|---|---|
| 작성 시간 | submitted_at − started_at |
| 오입력·재입력 횟수 | edit_count |
| 완료 화면 제시 후 수령까지 시간 | linked_at − 접수 번호 조회 시각 (조회 기록의 `receipt_view`) |
| 직원의 웹앱 입력 시간 | 대신 입력의 submitted_at − started_at |
| 응대 시간 | ended_at − started_at |

웹이 잴 수 없는 것은 현장 관찰로 잰다. 직원이 여객에게 다가간 순간부터 스캔까지의 시간, 직원이 다시 물은 횟수, 안내데스크 대기 시간이 여기에 해당한다.

### 5.4 번호 네 자리의 규칙

| | 접수 번호 | 패스 번호 |
|---|---|---|
| 범위 | 0000~9999 무작위 | 0000~9999 무작위 |
| 겹치면 안 되는 범위 | 패스 연결을 기다리는 등록끼리 | 살아 있는 패스(미사용·사용 중)끼리 |
| 번호가 다시 풀리는 때 | 패스를 연결했을 때, 또는 24시간 뒤 삭제될 때 | 패스가 끝났을 때(출발 후 만료, 분실 폐기) |
| 동시 발급 | DB의 고유 색인이 막는다. 겹치면 다시 뽑는다 | 같음 |
| 못 만들 때 | 20번 다시 뽑아도 겹치면 등록하지 않고 "접수 번호를 만들지 못했습니다. 잠시 후 다시 시도해 주세요"를 보여준다 | 패스 생성 작업이 오류로 끝난다 |

동시에 살아 있는 번호가 수천 개에 이르면 다시 뽑는 횟수가 늘어난다. 시범 규모(하루 수십 건)에서는 문제가 없고, 하루 등록이 천 건을 넘는 규모가 되면 자릿수를 늘린다.

## 6. 접근 통제

| 규칙 | 기본값 |
|---|---|
| 직원 로그인 | 접속 코드 두 가지. 현장 직원 공통 코드(로그인 뒤 근무 구역을 고르고, 근무 중에 바꿀 수 있다)와 안내데스크 코드. 로그인 유지 12시간이며 구역을 바꿔도 늘어나지 않는다. 구역을 고르기 전에는 여객 정보가 열리지 않는다. 예전의 구역별 코드도 그대로 쓸 수 있다 |
| 접속 코드 입력 실패 | 같은 기기에서 5회, 또는 같은 접속 주소에서 20회 틀리면 10분 차단. 기기는 접속 주소와 브라우저 표시로 구분하는데, 브라우저 표시는 바꿀 수 있으므로 접속 주소 기준을 함께 둔다. 공항 안에서는 여러 직원이 한 주소를 쓰므로 주소 쪽은 넉넉하게 둔다 |
| 패스 번호 입력 | 로그인한 직원만 가능. 접속 코드와 같은 기준으로 차단, 기록 |
| 여객 등록 | 같은 접속 주소에서 10분에 20건까지. DB 의 기록으로 센다 |
| 패스 번호 조회 범위 | 여객 카드를 여는 조회는 사용 중인 패스만. 안내데스크의 연결·재발급은 미사용 패스만 |
| 접수 번호 조회 | 안내데스크 권한 구역만. 연결 대기 중인 건만 |
| 여객 카드 표시 시간 | 조작 없이 2분 지나면 목록으로 돌아감 |
| 미연결 패스 | 아무 정보도 열지 않음 |

기본값은 기업탐방에서 기관 기준을 확인한 뒤 설정값만 바꾼다.

**모의 데이터 모드**

- 환경 설정 `DATA_MODE=mock`으로 켠다. 시범 기간에는 이 값으로 고정한다.
- 모든 화면 위에 "시범 운영 · 모의 데이터" 띠를 띄운다.
- 등록 화면의 이름 입력란에 "실제 이름을 입력하지 마세요"를 표시한다.
- 실제 정보 전환(`DATA_MODE=live`)은 기관 검토가 끝난 뒤에만 한다.

## 7. 운항 정보 연동

### 7.1 수집

- 대상: 공공데이터포털 여객기 운항 현황 상세 조회 서비스, 출발편
- 주기: 5분
- 범위: 오늘과 내일
- 편을 구분하는 기준은 예정 출발의 한국 날짜와 편명이다. 이 둘이 같으면 같은 편으로 보고 그 행만 갱신한다.
- 수집은 행을 지우지 않는다. 응답에 없는 편은 그대로 둔다. 오래된 편은 삭제 작업이 예정 출발 3일 뒤에 지운다.
- 갱신하는 항목은 항공사, 목적지, 터미널, 탑승구, 예정·변경 출발 시각, 상태 문구다.
- 탑승구가 이전 값과 다르면 이전 탑승구와 변경 시각을 남긴다. 미정에서 처음 배정된 것은 변경으로 보지 않는다.
- 응답에서 탑승구가 비어 오면 알고 있던 탑승구를 지우지 않는다.
- 한 쪽이라도 받지 못하거나 오늘·내일 출발편이 0건이면 그 회차 전체를 실패로 보고 아무것도 갱신하지 않는다. 기존 정보는 그대로 남고, 화면의 기준 시각이 갱신되지 않아 7.2의 경고로 이어진다.
- 매 실행 결과를 flight_polls에 기록한다.

### 7.2 화면 표시

| 상황 | 표시 |
|---|---|
| 정상 | "운항 정보 14:35 기준" |
| 받은 지 15분이 넘음 | 안내: "탑승구는 전광판에서 한 번 더 확인하세요" |

### 7.3 계산

- 탑승 마감 추정 = 변경 출발 시각(없으면 예정 출발 시각) − 10분. 10분은 설정값이다.
- 공공데이터의 상태가 `탑승마감`이면 추정 대신 "탑승 마감됨"으로 표시한다.
- 상태가 `탑승중` 또는 `마감예정`이면 남은 시간과 무관하게 임박으로 보고 목록 위쪽에 붉게 표시한다. 상태 문구는 남은 시간 옆에 그대로 보여준다.
- 공동운항: 여객이 입력한 편명이 공동운항 편명이면 실제 운항 편의 탑승구와 시각을 쓴다. 화면에는 여객이 입력한 편명을 보여주고 운항 편명을 덧붙인다.

- 직원 접속 코드를 12개에서 2개로 줄였다. 현장 직원은 공통 코드로 들어와 근무 구역을 고르고, 안내데스크는 안내데스크 코드를 쓴다(D8, 6장).
- 직원 목록에서 전체 구역을 보고 이름·편명으로 찾을 수 있다(4.4).
- 안내데스크에 패스 자동 배정을 넣었다(4.3).
- 등록 화면에서 편명을 두 글자 이상 치면 후보가 자동으로 뜬다. 찾기 버튼을 없앴다. 정확히 같은 편명이 맨 위에 오고 여덟 편까지 보여준다.
- 등록에 "확인" 단계를 더해 5단계가 되었다. 제출 전에 이름·항공편·구분·도움을 한 화면에서 보고 단계별로 고칠 수 있다.
- 등록 완료 화면에 접수 번호와 함께 이름·편명·도착지·출발 시각을 보여준다. 안내데스크 직원이 한눈에 대조한다.

**새로 넣은 것**

- 등록 내용 고치기(4.3), 여객 카드의 앞선 응대(4.4), 목록의 응대 중·응대 완료 표시(4.4), 안내데스크 오늘 현황(`/staff/desk/stats`).
- 오늘 현황은 지금 패스를 기다리는 등록, 패스를 쓰고 있는 여객, 오늘 받은 등록과 경로별 건수, 작성 시간과 패스 연결까지 걸린 시간의 가운데값, 여객 카드를 연 횟수, 응대 완료, 응대 시작까지 걸린 시간, 응대 시간, 두 구역 이상이 이어서 응대한 여객 수를 보여준다. 이름·편명·필요한 도움은 쓰지 않는다.
- 첫 화면(`/`), 없는 주소 안내 화면, 오류 안내 화면, 홈 화면에 추가할 때 쓰는 아이콘.

**영어 등록**

- 첫 화면 오른쪽 위에서 영어로 바꿀 수 있다(`/?lang=en`). 첫 화면, 등록 5단계, 완료 화면이 영어로 나온다.
- 저장되는 것은 항목 코드다. 여객이 영어로 골라도 직원 카드와 안내데스크에는 한국어 문구로 보인다. 직원 화면은 한국어만 쓴다.
- 운항 정보의 도착지 이름은 한국어뿐이라 영어 화면에서는 공항 코드(JFK 등)를 보여준다.
- 영어 문구는 `src/lib/i18n.ts` 에 있다. 선택 항목을 고치면 한국어(`catalog.ts`), 영어, 종이 체크리스트를 함께 고친다. 항목마다 영어 문구가 빠지지 않았는지는 자동 검사가 본다.
- 영어 문구는 팀이 한 번 읽어 보고 기관의 표기와 맞춰야 한다. 종이 체크리스트 영어판은 아직 없다.

**카메라 스캔 고침**

- 카메라를 1920x1080 으로 청하고(기기가 못 맞추면 가까운 값), 화면 가운데를 잘라 원래 해상도로 읽는 것과 전체를 줄여 읽는 것을 번갈아 한다.
- 이전에는 기본 해상도(보통 640x480)로 열어 전체를 줄여 읽었다. 2.5cm 패스 QR 을 20~30cm 에서 비추면 QR 한 칸이 2~3화소밖에 안 되어 읽히기 어려웠다. 10월 6일에 인식되지 않던 원인으로 보이지만 실제 휴대전화로 다시 확인한 것은 아니다.
- 화면 점검에 "1920x1080 화면 한가운데 170화소 크기의 QR" 장면을 넣었고 읽힌다.

**코드 검토 뒤 고친 것**

- 인계: 다음 구역 직원이 응대 시작을 누르면, 앞 구역이 완료를 누르지 않고 둔 응대는 그 시각에 끝난 것으로 한다. 직원이 자리를 옮기거나 구역을 바꿔도 "응대 중"이 계속 남지 않는다.
- 오늘 현황의 "구역을 이어서 응대한 여객"은 응대 시작을 누른 것만 세고 안내데스크는 뺀다. 출발해 지워진 여객은 이 수에서 빠진다.
- 전체 목록 조회 기록은 구역이 다르면 따로 남기고, 안내데스크가 여객 목록을 볼 때도 남긴다.
- 자동 배정에서 두 안내데스크가 동시에 같은 패스를 집으면 다음 패스로 다시 해 본다.
- 그 밖에: 늦게 도착한 옛 목록 응답 버리기, 앞 화면의 오류 문구가 다음 화면에 남던 것, 연결에 실패하면 찍어 둔 패스를 그대로 두기, 편명 검색에서 서버 오류를 "없는 편"으로 보이던 것, 스캔 화면을 바로 떠났을 때 읽기가 계속 돌던 것.
- 고치지 않고 남긴 것: 같은 구역의 두 기기가 같은 순간에 한 여객의 카드를 열면 응대 기록이 두 줄 생길 수 있다. 안내데스크에서 등록을 고치면 여객의 "되돌아가 고친 횟수"에 한 번이 더해진다. 이미 떠난 편으로는 화면에서 고칠 수 없지만 서버는 막지 않는다.
- 배포 순서: 테이블이 바뀌는 판을 올릴 때는 올린 직후 초기 설정(`scripts/remote-setup.ts`)을 다시 돌린다. 그 사이 1~2분은 로그인이 안 될 수 있다.

**화면 디자인**

- 공항 표지판과 탑승권에서 가져온 모양으로 전체를 다시 그렸다. 탑승구는 노란 판에 굵은 숫자로, 마감 30분 이내는 붉은 판으로 보여준다. 접수 번호와 여객 카드는 절취선이 있는 탑승권 모양이다.
- 한 화면에 가장 중요한 버튼은 하나이고 엄지가 닿는 아래쪽에 붙여 두었다.
- 선택 항목마다 그림을 붙였다. 오류와 주의는 색만이 아니라 그림과 함께 보여준다.
- 글꼴은 Pretendard, 숫자는 Barlow Condensed 다. 누르는 것은 모두 높이 44px 이상이다.

**검증**

- 업무 규칙 자동 검사 188개(`npm test`).
- 화면을 실제 브라우저로 처음부터 끝까지 눌러 보는 점검(`scripts/e2e.ts`). 2026-10-07 기준 150개 항목이 모두 통과했다. 여객 등록 5단계와 영어 등록, 로그인 전 차단, 공통 코드와 구역 고르기, 목록·전체·검색, 여객 카드와 응대 기록, 안내데스크의 접수 번호 조회·자동 배정·번호 연결·대신 등록·고치기·취소·재발급·패스 추가, 앞선 응대, 오늘 현황, 인쇄 모양(QR 25mm), 카메라 QR 스캔, 기본 카메라 경로(`/p/{token}`), 접속 코드 잠금, 통신 끊김 안내, 여객 카드 2분 뒤 자동 닫힘, 등록 취소 확인 창을 다룬다. 항목과 결과는 `docs/scenario-checklist.md` 에 실행할 때마다 다시 적힌다.
- 그림을 뜨는 화면마다 접근성 자동 점검(axe-core, WCAG 2.2 AA 규칙)을 함께 돌린다. 대비·이름표·역할 같은 것만 잡으며, 화면 읽기 프로그램으로 실제로 써 보는 것을 대신하지 않는다.
- 이 점검은 개발 컴퓨터의 모의 운항으로 돈다. 배포 주소에서 로그인한 뒤의 화면은 사람이 확인해야 한다.
- 패스 인쇄는 A4 PDF 로 떠서 QR 이 25mm, 한 줄에 4장으로 나오는 것까지 확인했다. 실제 프린터와 종이로는 아직 찍어 보지 않았다.
