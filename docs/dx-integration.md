# DX 통합 요청 1차 구현 — 2026-10-25

## 이번 구현의 기준

사전등록을 유지하고, 현장에서 필요한 서비스를 요청한 뒤 직원이 처리 상태를 공유하는 흐름에 무게를 둔다. 사전등록은 요청을 빠르게 만드는 선택 수단이다. 기본 도움 요청에는 항공편이나 증빙서류가 필요하지 않다.

이 버전은 공모전 시연용이다. 실제 공항 서비스 배정이나 로봇·전동차 제어와 연결되지 않는다. 장소·시설 자료는 기존 `airport.ts`의 모의 자료다.

## 새 화면

| 경로 | 역할 |
| --- | --- |
| `/help` | 미등록 여객의 현장 요청. 한국어·영어, 큰 글씨, 소리 안내 |
| `/help?place=cc-center` | 장소 QR에서 지정한 위치를 미리 선택. 여객이 확인·변경 |
| `/p/{token}/help` | 사전등록의 선택·인원을 불러와 확인·수정한 뒤 별도 요청 접수 |
| `/help/receipt/{receipt}` | 공용 화면의 QR을 휴대전화로 찍어 해당 요청 상태를 이어 확인 |
| `/staff/requests` | 접수·배정·이동·도착·지원·종료, 사유와 담당 구역, 당일 현황 |
| `/staff/requests/new` | 안내데스크가 여객 대신 접수. 공용 화면 비우기와 휴대전화 QR |

기존 `/register`, 패스·체크인·우대출구, 키오스크, `/staff` 호출, `/staff/assist` 이동지원은 유지한다. 기존 호출·이동지원 데이터와 새 통합 요청을 자동 변환하거나 합산하지 않는다. 직원 메뉴에서도 구분한다. 과거 흐름까지 하나의 큐로 옮기는 것은 별도 단계다.

키오스크 설치 세션에서는 위치를 서버에서 강제한다. 공용 화면은 90초 무입력 후 30초 확인을 거쳐 비운다. 화면을 비워도 이미 접수된 요청을 취소하지 않는다.

## 요청과 처리

`접수 → 배정 → 이동 중 → 도착 → 지원 중 → 완료`

- 배정 전에는 담당 구역·도착 시간을 확정하지 않는다.
- 진행 중인 요청의 위치가 바뀌면 취소 후 새로 접수한다.
- 취소와 지원 불가는 완료와 별도 집계한다. 지원 불가에는 사유가 필요하다.
- 담당 구역만 상태를 진행할 수 있다. 안내데스크는 지원 시작 전 배정을 해제하고 다시 접수 상태로 돌릴 수 있다. 이미 종료된 요청은 새로 접수한다.
- 상태 버전으로 동시 배정·중복 클릭 충돌을 검출한다. 충돌 시 새 목록을 확인한다.
- 새 요청에 대한 직원 화면 확인은 5초 간격이다. 네트워크 장애를 요청 취소로 표시하지 않는다.
- 1시간 미배정 또는 3시간 상태 변화가 없는 진행 요청은 `expired`로 종료한다. 자동 완료로 집계하지 않는다. 이 값은 시연 기준이며 현장 운영 기준 합의가 필요하다.

## 보관과 재시도

- 브라우저가 256비트 무작위 확인값을 제출 전에 저장한다. 서버에는 해시만 저장한다. 같은 값의 재시도는 처음 요청을 돌려준다.
- 일반 여객의 확인값은 탭의 sessionStorage에 보관한다. 공용 기기의 QR은 해당 요청의 확인 권한이므로 다른 사람에게 공유하지 않는다.
- 사전등록 하나에 진행 중인 통합 요청은 하나만 만든다. 별도 미등록 요청은 IP 해시별 10분 20건 제한을 원자적으로 적용한다.
- 요청 상세는 24시간 뒤 접근을 차단하고 정리한다. 사전등록 삭제·만료 시 연결된 상세도 제거한다. 연결 정보가 제거된 종료 기록은 90일 뒤 삭제한다.
- 정리는 요청 API와 기존 purge cron에서 실행한다. 사용하지 않는 기록의 실제 DB 삭제는 다음 정리 실행 시점에 이뤄진다.
- 이름·연락처 입력란은 없다. 추가 말씀은 200자이며 화면에 불필요한 개인정보를 적지 않도록 안내한다.

## 직원 알림

화면 내 소리·진동은 직원이 켠 뒤 새 접수에만 반응한다. 별도 브라우저 푸시는 다음 서버 환경변수 세 개가 있을 때만 활성화한다.

```text
WEB_PUSH_PUBLIC_KEY=<VAPID 공개 키>
WEB_PUSH_PRIVATE_KEY=<VAPID 비공개 키, 서버 전용>
WEB_PUSH_SUBJECT=mailto:<운영 연락 주소>
```

직원이 자기 기기에서 버튼을 눌러 권한을 허용해야 등록한다. 구독은 근무 구역과 로그인 만료에 연결하며, 로그아웃하면 해당 세션 구독을 지운다. 알림에는 새 요청이 있다는 사실만 표시한다. 직원 상세는 로그인한 화면에서 확인한다. 푸시 실패는 요청 접수를 취소하지 않는다. 세 값이 비어 있으면 화면 내 알림을 안내한다.

전용 service worker는 `/staff/` 범위이며 직원 화면·API를 캐시하지 않는다. 기존 패스 오프라인 worker와 범위를 분리했다. 잠금 상태와 실제 모바일 기기 수신은 배포 환경에서 별도 확인해야 한다. 키 생성·등록이나 실제 외부 발송은 이번 로컬 검사에서 수행하지 않았다.

## 배포 순서

1. 별도 preview DB에 먼저 적용한다. `db/schema.sql`은 기존 표를 지우지 않는 추가 스키마다. 새 표는 `service_requests`, `service_request_limits`, `request_push_subscriptions`다.
2. 목표 DB 연결 문자열을 안전하게 환경에 설정하고 `npm run db:migrate -- --remote`로 스키마만 적용한다. 기존 admin setup/seed로 운영 자료를 다시 넣지 않는다.
3. Vercel preview에 코드를 배포한다. preview DB·세션 키·실제 공개 주소 `BASE_URL`을 맞춘다. `DATA_MODE=mock`을 유지한다.
4. `/help` 접수, 직원 배정, 여객 상태 반영, QR의 실제 휴대전화 접속, 취소·지원 불가·로그아웃을 확인한다.
5. 검증 뒤 main 병합과 production 배포를 진행한다. production에도 코드보다 먼저 추가 스키마를 적용한다.

로컬 내장 DB는 자동 마이그레이션한다. `JSP_LOCAL_DB_DIR`을 지정하면 기존 `.data/pglite`와 독립된 검증 DB를 사용할 수 있다. 내장 DB를 동시에 여러 프로세스로 열지 않는다.

## 검사 방법

GitHub PR과 main 푸시는 `.github/workflows/ci.yml`에서 lint·단위 검사·운영 빌드를 실행한다. 운영 비밀값이나 DB 연결 문자열을 사용하지 않는다. 실제 브라우저·기기 검사는 아래 로컬 절차로 별도 실행한다.

```text
npm run lint
npm test
npm run build
```

브라우저 검사는 실제 운영 DB와 분리한 모의 서버에서만 실행한다. `scripts/dx-e2e.ts`는 모의 운항·시범 코드를 준비하므로 배포 서버에서 실행하지 않는다. 새 브라우저 검사 둘은 localhost/127.0.0.1만 허용한다.

`npm run test:dx:server`는 운영 DB·외부 푸시·운항 API 설정을 비우고, `.data/dx-browser-checks`의 별도 DB로 127.0.0.1:3100에서 실행한다. 먼저 빌드하고, 이 서버에서 `dx-e2e.ts`로 시범 데이터를 준비한 다음 나머지 검사를 실행한다. 다른 터미널에서 다음 명령을 쓴다.

```powershell
$env:E2E_BASE='http://localhost:3100'
$env:E2E_CRON_SECRET='dx-local-check-only'
npx tsx scripts/e2e.ts
npx tsx scripts/dx-e2e.ts
npx tsx scripts/dx-resilience-e2e.ts
```

테스트 서버의 `CRON_SECRET`은 위 검증용 값, `BASE_URL`은 `E2E_BASE`와 같게 설정한다. 브라우저 검사 두 개는 로컬 Chrome/Edge 설치가 필요하다. 단위 검사는 외부 푸시 발송을 mock으로 대체한다. 실제 로봇 API·항공사 체크인·운영 위치 검증·기기 잠금 상태의 푸시 수신은 자동 검사 범위에 없다.
