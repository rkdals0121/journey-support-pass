# 예약 조회와 지원등록 연결

작성: 2026-10-27. 현재 구현은 가상 예약 시연이며 실제 항공사 API는 연결하지 않는다.

## 현재 시연

`/prepare/booking`에서 시연 항공, 예약번호 `DEMO01`, 영문 성 `KIM`으로 조회한다. `시연값 넣기`로 채울 수도 있다. 결과는 다음 날 한국 시간 18:00 출발, 인천→도쿄(NRT), 가상 편명 DX9001이다. `DEMO02 / LEE`는 취소 사례다.

조회 → 결과 확인 → 이 항공편으로 지원등록 → 기존 지원 질문 → 항공편 확인 → 등록 완료 → 패스 발급으로 이어진다. 기존 항공편 직접 선택 경로도 유지한다. 패스 발급은 도움 필요 정보를 등록하는 것이며 항공권이나 현장 서비스 예약 확정이 아니다.

조회는 DB를 변경하지 않는다. 사용자가 동의하고 최종 등록을 제출할 때만 가상 운항편을 준비하고 기존 등록·패스 발급 처리를 실행한다. 날짜·편명이 기존 자료와 충돌하면 덮어쓰지 않고 직접 선택을 안내한다. 동일 날짜의 가상 편은 하나만 생성한다.

## 전달 계약과 저장

입력 계약: `{ airline, reference, surname }`. 현재 허용 항공사는 `demo` 하나다. 응답은 `BookingHandoff`: `mode`, 정규화된 `flight`, 서명된 `context`, `expiresAt`이다. 예약번호와 영문 성은 응답·URL·브라우저 저장소·등록 DB에 남기지 않는다. 조회 성공 후 입력 상태도 비운다. 조회 요청 본문 최대 2KB, 응답은 no-store다.

서버는 목적이 지정된 HMAC 전달값을 발행한다. 가상 편 날짜·발급 시각·만료 시각만 포함하며 유효기간은 30분이다. 최종 제출에서 서명, 만료, 날짜·편명 일치, mock 모드, 웹 접점, 동의·선택 항목을 검사한다. 이는 신원 증명 수단이 아니다. 만료되면 다시 조회하며 입력 중인 등록은 처음부터 시작한다. 직접 항공편을 바꾸면 해당 전달값을 보내지 않는다.

## 실제 연동 시 교체할 경계

현재 `lookupDemoBooking`은 외부 호출이 없는 시연 제공자다. 실제 제공자는 항공사와 계약한 서버 전용 어댑터로 별도 구현한다. 항공사별 필수 항목·예약번호 체계·공동운항·복수 구간·취소 상태·탑승객 선택을 명시적으로 정규화해야 한다. API 키를 브라우저에 전달하지 않는다. 실제 모드에서는 현재 시연 조회·시연 운항 생성이 모두 차단된다.

예약 완료 후 연결 방식은 제휴사가 발행한 일회성 코드를 서버에서 교환하고, 발행자·대상·만료·재사용 여부를 검증한 뒤 필요한 항공편만 전달받는 구조로 설계한다. URL에 예약번호·이름·지원 필요 정보를 싣지 않는다. 실제 제공자의 검증·동의·보관 기준이 마련되기 전에는 실제 예약 조회 완료 표시를 하지 않는다. 실연동에는 별도 환경 설정, 기관 승인, 호출 제한과 장애 시 직접 선택 경로 검증이 필요하다.

## 화면 원칙

탑승권·전자항공권 스캔은 다음 입력 보조 경로로 설계한다. 기기 안에서 편명·출발일 후보를 추출하고 이용자가 확인한 뒤 기존 항공편 선택에 넣는다. 스캔만으로 예약 유효성을 검증했다고 표시하지 않는다. 현재 추가한 데모 조회와는 별개이며 이 변경에는 새 스캔 기능을 구현하지 않았다.

조회 화면은 기능 제목·입력·결과·다음 행동만 남긴다. 전역 노란 띠는 사용하지 않는다. 시연 안내는 조회 화면과 해당 가상 편이 선택된 등록 화면에 표시한다. PC는 예약번호·영문 성을 한 줄에, 모바일은 세로로 배치한다. 초록색 주 행동과 기존 해바라기 정체성을 유지한다. 서비스 찾기·직원·키오스크의 다른 업무 흐름은 별도로 유지한다.

## 검증 범위

정상 조회·잘못된 조회·취소·실제 모드 차단, 서명 변조·만료·편명 불일치, 동시 생성·기존 편 충돌, 동의 전 생성 방지, 지원등록과 패스 실제 발급, 예약 식별자 미저장을 단위/DB 검사로 확인한다. 브라우저에서는 모바일·PC의 입력/결과 배치와 조회에서 패스 발급까지 확인한다. 운영 배포에서는 조회와 화면만 확인하고 임의의 실사용 접수는 만들지 않는다.
