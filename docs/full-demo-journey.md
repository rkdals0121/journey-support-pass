# 공모전 전체 시연: 같은 등록·같은 접수의 연결

대표 흐름은 사전등록한 여객이 공항에서 이동지원을 요청하고, 안내데스크가 배정·장비 연결·구역 인계를 처리한 뒤 여객과 운영자가 같은 결과를 확인하는 장면이다. 실제 로봇·차량 제어, 항공사 예약 자동 수신, 외부 부서 API 수신 확인은 시연 범위가 아니다.

## 사전 준비

안내데스크는 `/staff/demo`에서 시연편을 준비한다. 여유 있는 기존 시연편은 재사용하고 없으면 약 3시간 뒤 출발하는 `DX####` 한 편을 추가한다. 기존 항공편을 갱신·삭제하거나 기존 등록을 초기화하지 않는다. 모의 데이터 모드·안내데스크 권한에서만 생성한다. 편명·출발일은 준비 화면에 표시된 값을 사용한다.

여객과 직원의 세션을 분리한다. 예: 여객 iPhone, 안내데스크 PC Chrome, 현장 직원 PC Edge. 같은 브라우저 프로필의 탭끼리는 로그인 쿠키를 공유하므로 직원 역할을 나누는 데 쓰지 않는다. 현장 직원 역할은 공통 코드로 로그인해 탑승동 중앙부를 선택하고, 인계 후 끝단으로 구역을 바꿔 연기할 수 있다. 동시 권한 검사는 자동 브라우저에서 별도 세션으로 확인한다.

장비 대장에서 시연용 이동지원 장비 한 대를 준비한다. 이는 내부 가용·배차 기록이며 실제 장비가 연결되었다고 설명하지 않는다.

## 본 시나리오

1. `/demo/booking` → `/prepare?via=booking` → 실제 등록 화면. 걷기·보기 어려움, 계단 없는 이동, 큰 글씨, 동행인 2명, 필요할 때 호출, 화장실을 고른다. 시연편과 준비 화면의 출발일을 선택한다. 서류는 사용하지 않는다. 메모를 입력하고 등록한다.
2. 등록 완료는 현장 요청 생성과 구분한다. 내 등록에서 ‘사전등록 내용으로 지금 도움 요청’을 누르고 탑승동 116번 앞을 만날 곳, 이동지원을 서비스, 130번 앞을 목적지로 고른다. 도움 항목·2명·메모를 불러온 것을 확인하고 최종 확인 후 접수한다.
3. 안내데스크가 같은 요청을 탑승동 중앙부에 배정하고 시연 장비를 배차한다. 현장 직원이 출발·도착을 기록하면 여객 화면이 바뀐다.
4. 안내데스크가 사유와 함께 끝단 구역에 인계한다. 진행 상태·장비는 유지한다. 이전 구역은 이후 처리 권한을 잃는다.
5. 끝단 직원이 지원을 진행하고 직접 확인한 처리 결과를 기록한다. 여객의 요청 화면과 내 등록에서 같은 결과를 확인한다. 완료 후 장비는 다시 가용 상태가 된다.
6. `/staff/overview`에서 담당 업무·완료 결과를 확인한다. 합계는 실제 DB 집계이며 사전등록 연결 접수를 별도 접수로 중복 합산하지 않는다.

## 이번 점검으로 수정한 것

- 사전등록의 메모가 현장 요청에서 비어 있던 연결을 수정했다.
- 일반·사전등록 진입에서 서비스만 선택한 요청도 해당 서비스의 업무 분류로 기록한다. 명시적인 기존 사업 지정 링크는 보존한다.
- 개인 현장 요청에서 내 등록으로 돌아가는 링크를 추가했다. 공용 키오스크의 복귀·다음 여객 분리 동작은 유지한다.
- 운영 사이트에 특정 모의 편명이 남아 있지 않아도 시연할 수 있도록 안전한 시연편 준비 화면을 추가했다.

## 검증 실행

`npm run build` → `npm run test:dx:server` → `npx tsx scripts/demo-journey-e2e.ts`.

스크립트는 로컬 주소에서만 실행한다. 사전등록을 API로 건너뛰지 않고 실제 입력 버튼과 직원 로그인·배정·인계·완료 버튼을 누른다. 준비용 구역 코드를 로컬 서버에 설정하고, 장비 한 대를 명시적인 모의 대장 기록으로 등록한다. 운영 DB나 외부 알림에는 접근하지 않는다.

별도 회귀 검사: `scripts/dx-e2e.ts`, `scripts/kiosk-dx-e2e.ts`, `scripts/business-resolution-e2e.ts`, `scripts/dx-resilience-e2e.ts`.

옛 `docs/scenario-checklist.md`의 300개 결과는 그 파일에 적힌 당시 화면의 검사 기록이다. 이번 전체 시연 결과를 그 옛 결과로 대신 설명하지 않는다.
