# 첫 화면 배치 개선 · 2026-10-30

시작 전 `git pull --ff-only origin main`으로 5785c72까지 갱신하고 `fix/viewport-fit-20261030`에서 작업했다.

## 발견과 수정

- 도움 요청: PC에서는 세 단계 입력을 한꺼번에 펼쳐 제목·설명·단계 표시 뒤에 입력칸과 제출 버튼이 밀려 있었다. 기존 모바일 단계 이동을 PC에도 적용하고, 같은 단계의 서비스 선택과 세부 입력을 나란히 배치했다. 마지막 단계에서 요약·동의·확인을 보여 준다. 이전 단계로 돌아가도 값은 유지한다.
- 길 찾기: PC 출발지·목적지를 나란히 배치하고 경로 버튼을 화면 하단에 유지한다. 선택한 출발지의 검색 도구는 다른 위치 찾기로 다시 펼칠 수 있다.
- 서비스 목록: PC 3열, 태블릿 2열, 휴대전화 1열로 읽는다. 카드의 강제 최소 높이와 제목·보조 영역의 과한 간격을 줄였다.
- 만남 예약: 기존 단계와 만남 거점은 그대로 유지한다. 등록 폼의 전역 label 여백 중복을 제거하고 지도와 범례를 같은 영역에서 읽도록 정리했다.
- 내 요청, 사전등록 안내, 예약 조회: 같은 공용 영역의 과한 여백을 줄였다.
- 공용 도움 요청의 키오스크 버튼은 64px 누르기 기준을 적용한다.
- 배치 검사에서 추가로 발견한 서비스 검색의 작은 버튼과 320px·글자 1.5배 등록 상단바 넘침도 수정했다.

## 검증

- TypeScript 통과, ESLint 오류 0개(기존 경고 3개).
- 로컬 단위 테스트 982개 통과, 5개 건너뜀. GitHub CI에서는 PostgreSQL 항목까지 987개 전부 통과했다.
- 실제 브라우저에서 390/1280/1920 너비로 휠체어 선택 → 위치 선택 → 뒤로 → 값 유지 → 확인 → 수정 흐름 통과. 길 찾기는 출발지·목적지 선택 후 실제 경로 결과를 확인했다.
- 기본 글씨의 1280×633/1366×657/1920×937 도움 요청 첫 단계는 입력칸과 다음 버튼이 첫 화면 안에 있는지 좌표로 확인한다.
- 최종 검증 결과는 아래에 정리했다.

큰 글씨, 좁은 휴대전화, 긴 선택 목록, 긴 신고 내용은 자연스럽게 스크롤한다. 페이지 전체를 배율이나 transform으로 축소하거나 내용을 잘라 한 화면에 억지로 맞추지 않는다. 첫 단계의 주요 선택과 진행 동작이 과한 공백 때문에 밀리는 문제를 고치는 범위다.

색상 메타데이터 상수와 실제 API·예약 거점·기관 연동 방식은 변경하지 않았다. 별도 작업자의 기존 변경 파일은 포함하지 않는다.

## 추가 확인

- 작업 중 main에 합쳐진 4ff1b28의 하늘이 메인 화면도 병합해 보존했다. 최신 메인 화면의 12개 크기·글자 조합은 별도 검사에서 문제 0개였다.
- 배치 전수 검사: 132개, 문제 0개. 로컬 프로덕션 빌드도 통과했다.
- Vercel 미리보기: 첫 화면·등록·직원 로그인·키오스크 모두 HTTP 200, 기대 제목·콘텐츠 표시, 브라우저 오류·500 응답 없음.
- 수정 화면 4개도 실제 Vercel 미리보기에서 1280/1920으로 열어 8개 상태가 모두 정상임을 확인했다.
- CSS 검토 중 작은 화면의 1열 규칙을 나중의 태블릿 규칙이 덮는 문제를 찾아 해당 중복 규칙을 제거했다. 태블릿 2열과 PC 3열은 유지한다. 휴대전화에 다시 적용되던 큰 제목·외곽 여백도 중복 선언을 제거해 정리했다.
- 전체 E2E 최초 실행은 오래된 검사 도우미가 새 키오스크 서비스 메뉴를 건너뛰어 135개 통과 후 중단했다. 도우미가 실제 메뉴를 눌러 개인 안내로 진입하도록 수정하고, 별도의 깨끗한 로컬 테스트 체크아웃에서 289개를 모두 통과했다.

- 이후 main에 합쳐진 81eadae까지 병합했다. 다른 작업자의 메인 비율, 안내 키오스크 첫 화면, 키오스크 예약 디자인을 보존했다. 최신 병합 뒤 해당 화면 배치와 미리보기도 다시 확인했다.
- 별도 로컬 검사 환경의 Next 개발 서버에서 첫 API 컴파일(등록 API 약 19초)이 화면의 기존 통신 제한 시간을 넘는 것을 확인했다. 화면의 통신 제한 시간이나 통과 기준은 바꾸지 않았다. E2E 시작 전에 API 모듈에 읽기 전용 준비 요청을 보내 프로덕션 빌드와 같은 준비 상태에서 전체 검사를 진행하도록 점검 도구를 보완했다.

기본 글씨의 도움 요청 첫 단계에서 `task-purpose` 입력칸과 다음 버튼을 실제 브라우저 좌표로 확인했다.

## 최종 결과

- 전체 기능 E2E: 289개 통과, 실패 0개. 입구 로봇 접수 → 통합 요청 저장 → 직원 화면 조회 → 배정 → 취소 기록까지 확인했다. 스크린샷 64장은 `e2e-final/`, 자동 생성 원본 보고서는 `e2e-checklist.md`에 저장했다.

- 최신 CI: 59개 테스트 파일, 단위 테스트 987개 전부 통과. 린트와 프로덕션 빌드도 통과했다. 기존 경고 3개는 이 수정 범위 밖에 남아 있다.
